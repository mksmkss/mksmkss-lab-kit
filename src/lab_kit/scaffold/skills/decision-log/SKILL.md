# 研究の経緯を issue に残す

**1テーマ = 1 issue。** 本文は「今の結論」、コメントは「決定の記録(時系列)」。後から「なぜそうしたか」を辿れるようにするのが目的。

| 場所 | 内容 | 更新 |
|---|---|---|
| 本文 | 現時点のまとめ(下の「まとめの型」)、AsIs/ToBe、検証計画 | **コメントを足したら、必ず書き換える** |
| コメント | 決定の記録(D1, D2…)、実験の経過、失敗・断念 | **追記のみ。書き換えない** |
| サブ issue(任意) | 数値や図を伴う大きな実験・決定を、単独で参照したいとき | 結論が出たら閉じる |

## 最初に確認すること

1. `gh auth status` が通るか。通らなければ、ユーザーに `gh auth login` を案内して止まる。
2. 対象リポジトリと公開範囲。リポジトリ名を直書きせず、次で取得する。
   ```bash
   gh repo view --json nameWithOwner,visibility --jq '.nameWithOwner + " " + .visibility'
   ```
   `PUBLIC` なら、**相談の記録(`meeting`)は作らない**。その他の記録も、データの内容や個人情報が入っていないか特に注意する。
3. ラベルが揃っているか(下記)。足りなければ作成を提案する。

## ラベル

**段階ラベル(必須・1つの issue に1つだけ)**

| ラベル | 意味 | 付けるとき | 色 |
|---|---|---|---|
| `idea` | 考え中。方針が未確定 | issue を作ったとき | `FBCA04` |
| `decided` | 方針が固まり、実装の直前 | 「変更内容」「検証計画」を本文に書いたとき | `1D76DB` |
| `doing` | 実装・実験中 | 作業を始めたとき | `F9A03F` |
| `done` | 完了 | 結果を残して閉じるとき | `0E8A16` |

段階が変わるときは、前のラベルを外して次を付ける。`done` で issue を閉じる。

**種類ラベル(任意・複数可)**: `experiment` `method` `data` `analysis`。ユーザーの研究に合わせて足してよい。

**相談ラベル**: `meeting`(段階ラベルは付けない。状態は open / closed で表す)。

足りないラベルの作成:
```bash
gh label list --limit 100
gh label create idea --color FBCA04 --description "考え中。方針が未確定"
```

## まとめは必ず更新する

コメントが増えると、結局どうなったのかが分からなくなる。**コメント(決定・結果・訂正)を足したら、そのターンのうちに、本文の「現時点のまとめ」を書き直す。** 読み手は、本文だけを読めば今の状態が分かるようにする。

- このルールは、フック(`.claude/hooks/summary_guard.py`)で確認される。コメントを足して本文を直さないと、ターンを終えられない。前のセッションで直せなかったものは、次の開始時に知らされる。
- 本文は `gh issue edit <N> --body-file <file>` で書き換える。直す前に、**必ず最新の本文を取得する**(`gh issue view <N> --json body --jq .body`)。
- 更新前のまとめは、本文の末尾の `<details>` に入れて残す(履歴)。
- 「最終更新」の日付と、反映したコメントへのリンクを、まとめの先頭に書く。

## まとめの型

本文の先頭に置く。上から順に読めば、目的 → 何をしたか → 何が分かったか → 次、が辿れるようにする。**やったことの紹介ではなく、目的に対する答えとして書く。**

| # | 節 | 書くこと |
|---|---|---|
| 1 | `## 現時点のまとめ(YYYY-MM-DD 更新)` | 見出しに日付。反映したコメントへのリンク |
| 2 | **ステータス**(太字1〜2文) | 何が完了し、何が未実施か |
| 3 | **一言** | 何を変えずに、何を試し、どれが基準を超えたか。数値つき。届かなかった点も書く。記号は、ここで使うなら同じ文の中で定義する |
| 4 | この記録の位置づけ | 何のための issue か、背景の issue へのリンク |
| 5 | 守る制約 | 変えないもの、使ってよいもの・いけないもの(リークなど)、評価の条件。誰がいつ決めたか |
| 6 | 最新の回の要点 | 直近の結果コメントへのリンクと、要点を3項目まで |
| 7 | 成功基準 | **実験の前に決めた**基準を、数値で(何を何と比べ、どの値を超えたら成功か) |
| 8 | 試したことの一覧 | 表: 内容 / 状態(完了・未評価・未実施)/ 結果へのリンク。失敗・設計不備も載せる |
| 9 | 結果 | 見出しに条件(設定、seed 数、件数)。図(commit sha 固定の URL)と、その下に見方1行。表は、基準との差と**判定**の列を付け、成功は太字 |
| 10 | 再現の確認 | 基準の値が、前の結果と一致したか |
| 11 | 各手法の内容 | 記法を先に定義し、式(LaTeX)で書く。結果の解釈は、推測なら推測と書く |
| 12 | 決定 | D番号ごとに1〜3行と、コメントへのリンク。自分の理解の誤りを訂正した決定も残す |
| 13 | 限界 | seed 数、独立でない引き直し、多重比較の補正の有無など |
| 14 | 未解決・次 | 番号つき。何が分かれば次に進めるか |
| 15 | 成果物 | コード・結果のパス、ブランチ、コミット、関連 issue |
| 16 | `<details>` 更新前のまとめ | 履歴 |

- 決めていない節は省いてよい。ただし 1・2・3・7・8・14 は必ず書く。
- 目的に関係しない結果は、本文に入れず、コメントか `<details>` に回す。
- 取り下げた説明・誤りは、まとめの「決定」か「限界」に残す(コメントの訂正だけにしない)。

例(架空):

````markdown
## 現時点のまとめ(2026-11-02 更新、[結果の記録 #3](<コメントのURL>) まで反映)
**ステータス: 推論側の案3つの評価が完了。学習をやり直す案は未実施。**
**一言:** 手法の学習は変えずに、判定の仕方だけを変える案を3つ試した。成功基準を超えたのは「案A」(F1 0.70 → 0.74)の1つだけ。件数の少ないクラスの F1 は、どの案でも基準(+0.05)に届かない。

この issue は、手法を良くするために試した手を、すべて記録する場所。背景は #3。

### 守る制約
- 手法の学習は変えない(相談の記録 #5)。
- 学習・選択に評価用の正解を使わない。

### 成功基準(実験の前に決めた)
現行との差で、F1 が +0.02 以上。

### 試したことの一覧
| 案 | 内容 | 状態 |
|---|---|---|
| 案A | しきい値をクラスごとに変える | 完了([#2](<URL>)) |
| 案B | スコアを補正する | 完了(基準未満) |
| 案C | 損失を変える | 未実施 |

### 結果(3 seed × 10回、test 1,000件)
| 案 | F1(現行との差) | 判定 |
|---|---|---|
| 現行 | 0.70 | 基準 |
| **案A** | **0.74(+0.04)** | **成功** |
| 案B | 0.71(+0.01) | 基準未満 |

### 未解決・次
1. 案A が、seed を変えても安定するか。

<details><summary>更新前のまとめ(2026-10-30)</summary>
...
</details>
````

## 書き方の規則

読み手は、自分と、後でこの issue を読む人(先生・共同研究者)。冗長にはしない。

- **用語は初出で定義する。** 実験中に付けた名前・記号(V2、K=3 など)は、「名前 = 内容」を1文か表で書いてから使う。
- **1つのものに、1つの名前。** 集まりは「名前 = 条件(件数)」で定義し、最後まで同じ名前を使う(例: 「正解が2つ以上あるデータ(120件)」)。件数だけ(「120件」)や、条件を省いた名詞(「平均を取るデータ」)を名前にしない。
- **違いは表で示す。** 昔と今、A と B を比べるときは、違う軸(何を数えるか、どの集まりで平均するか、しきい値の決め方)を行にする。同じ点も1行で「同じ」と書く。
- **表の見出し・行名・列名にも、同じ規則を使う。** 指標名には、何の値か(0.5 なら何、1.0 なら何)を添える。
- **結果は問いごとに「答え → 根拠の表 → 意味」。** 各節の終わりに、目的に対して何が言えるか・まだ言えないかを1〜2文で書く。
- **比喩を使わない。** 「足し算にならない」ではなく、「両方使っても、単独のときより良くならなかった(+0.012 対 +0.016)」と書く。
- **自分の作業手順の言葉(「プールする」「引き直す」など)を、説明なしで使わない。**
- **変種の一覧にしない。** 筋(ギャップ → 仮説 → 試したこと → 分かったこと)で書き、変種名は括弧に添える。
- **問題・課題・手段を取り違えない。** 問題 = 目的と現状のギャップ。課題 = それを埋めるために取り組むこと。手段 = 課題の解き方。
- **通じなかったら、言い換えを重ねない。** 用語の定義と、1件を通した具体例で説明し直す。

## 数式は LaTeX で書く

- 文字だけの式(`a_1`、`s_il`)を使わない。式は言葉で言い換えて消さず、残す。
- **インラインは `` $`式`$ `` の形にする。** 普通の `$式$` は、前後が日本語の文字や「、」「。」だと描画されない。
- **別行の式は ` ```math ` のコードブロックにする。** 前後に空行を入れ、箇条書きの中に入れず、字下げしない。`$$` は、直前に空行がないときや、字下げしたときに崩れる。
- 表の中の式に `|` を入れない(絶対値は `\lvert ... \rvert`)。
- コードの識別子(`overall_f1`)はバッククォートで書き、数式にしない。
- 投稿後に、描画を確かめる。`gh api repos/<owner>/<repo>/issues/<N> -H "Accept: application/vnd.github.html+json" --jq .body_html` に、生の `$$` や `` $` `` が残っていないかを見る。

## Claude が自分の判断で試したこと

ユーザーの指示ではなく、Claude が自分で考えて試した手(うまくいかなかったもの・設計不備のものを含む)は、**専用のテーマ issue に全部残す**。他の issue に混ぜない。

- まとめの「試したことの一覧」に、状態(完了 / 未評価 / 未実施)を付けて並べる。
- 成功基準は、実験の前に決めて書く。
- ユーザーが方向を指示したら、その指示と、前の理解の誤りを、決定(D)として残す。

## 最重要ルール: 決定は背景まで全部残す

**決定は、結論だけでなく、背景・根拠・検討した代替案・影響まで残す。**

- **いつ**: ユーザーが方針・設定・データ・評価・手法について何かを決めたとき。次の作業に進む前に残す。会話の区切りでも、未記録の決定がないか確認する。
- **失敗・断念も残す**: 試したが使えなかったものは、理由とともに残す。
- **事実と推測を分ける**: 確認したことと、推測にとどまることを混ぜない。確認していないことは「未確認」と書く。
- **成果物の場所を残す**: 生成したデータ・スクリプト・図のパスと、件数などの検証値。
- **過去の決定との関係を確認する**: 新しい決定が、過去の決定を置き換える・前提にする場合は、決定の記録に `#番号` / `D番号` で書く(GitHub が相手側のタイムラインに自動で参照を出す)。置き換えられた決定は消さず、状態を「置き換えられた」にして一覧に残す。

### 決定の記録(コメント1件)

```markdown
## D<N>. <決定を一言で>
- **決定**: <何をどうするか>
- **決定者**: <自分 / 先生との相談 #N / 共同研究者名など>
- **背景**: <なぜ必要になったか>
- **根拠**: <データ・コード・数値。ファイルパス、件数、seed>
- **検討した代替案**: <案と、採らなかった理由>
- **影響・残る問題**: <できなくなること、未確認のこと>
- **過去の決定との関係**: <なし / D2 を置き換える / #12 が前提>
```

D番号は、そのテーマ内で連番にする。

## 操作

本文・コメントは一時ファイル(scratchpad)に書いてから `--body-file` で渡す。**投稿の前に下書きをユーザーに見せ、承認を得る。** ただし、ユーザーが「残して」「記録して」と明示的に頼んだ決定の記録は、依頼そのものを承認とみなして投稿してよい(投稿後に内容を報告する)。

### A. テーマ issue を作る(`idea`)

既存の関連 issue があれば、新規作成せずそちらを更新する(`gh issue list --search "<語>" --state all`)。

本文テンプレート(結果が出る前。結果が出たら「まとめの型」の節を足していく):
```markdown
## 現時点のまとめ(YYYY-MM-DD 更新)
**ステータス:** <未着手 / 検討中>
**一言:** <今の結論を1〜2文。決まっていなければ「未定」>

この issue は <何のためか>。背景は <#N>。

### 守る制約
- <変えないもの、使ってはいけないもの>

### 成功基準(実験の前に決める)
- <何を何と比べ、どの値を超えたら成功か>

### 決定
| D | 決定 | 状態 | 出どころ |
|---|---|---|---|

### 未解決・次
1. **<論点名>**: <何が決まっていないか、なぜ重要か>
```
```bash
gh issue create --title "<タイトル>" --body-file <本文ファイル> --label idea
```
- **決定事項と未確認事項を混ぜない。** コードを読んでいない箇所は「未確認」と書く。
- 数値・結果を載せるときは、seed・データ件数・設定も一緒に書く。

### B. 決定を追記する

1. 決定の記録(上のテンプレート)をコメントとして投稿する。
   ```bash
   gh issue comment <N> --body-file <コメントファイル>
   ```
2. **続けて、本文のまとめを更新する**(現在の本文を取得 → 編集 → 反映)。「まとめの型」に沿って、ステータス・一言・決定・未解決を直し、前のまとめは `<details>` に移す。コメントだけで終わらせない(フックが止める)。
   ```bash
   gh issue view <N> --json body --jq .body > <本文ファイル>
   gh issue edit <N> --body-file <本文ファイル>
   ```

### C. 実装に入る(`idea` → `decided`)

論点が解消し、何をどう作るかが決まったら、新しい issue は作らず、本文に次を足してラベルを付け替える。

```markdown
## 変更内容
- 意図: <なぜ 1〜2行>
- 対象ファイル: <パス>

| 項目 | AsIs | ToBe | 根拠 |
|---|---|---|---|
| <観点> | <変更前> | <変更後> | D2 |

## 検証計画
- [ ] <再現条件: seed、データ件数、設定>
- [ ] <確認する指標と、成功の基準(実験の前に決める)>
```
```bash
gh issue edit <N> --body-file <本文ファイル> --add-label decided --remove-label idea
```
- AsIs/ToBe は結論だけを書き、**理由は D のコメントに書く**(「根拠」列で D番号を参照)。
- 方針が変わったら、本文の表を書き換え、**変わった理由を新しい D に追記する**。
- 手法の変更を伴わない issue(分析・データ作成など)では、この節を省略してよい。
- コミットからは `Refs #N` で参照する。

### D. 作業を始める・終える

- 始める: `gh issue edit <N> --add-label doing --remove-label decided`
- 終える: 結果を最終コメントに書き(結果の説明は `explain-results`、図は `result-graphs`)、`gh issue edit <N> --add-label done --remove-label doing` の後で `gh issue close <N>`。

### E. 相談の記録(`meeting`)

相談は研究のテーマと別の軸なので、**相談ごとに1つの issue** にする。複数のテーマを話すことが多いため、テーマ issue のコメントに混ぜない。**公開リポジトリでは作らない。**

- **相談の前**: 題は `YYYY-MM-DD 先生との相談`。`meeting` ラベルを付けて作る。
  ```markdown
  ## 相談したいこと
  1. <論点。関連するテーマ issue: #N>
     - 現状: <結果・図へのリンク>
     - 聞きたいこと: <何を決めたいか>
  ```
- **相談の後**: コメントに追記する。**先生の発言と自分の解釈を分け**、聞き違いがあれば訂正できるようにする。
  ```markdown
  ## 指摘・決まったこと
  - 先生の指摘: <発言> (論点 1)
  - 私の理解: <解釈。不確かなら「未確認」>
  - 決定: <何をどうするか> → 反映先: #N の D<番号>

  ## TODO
  - [ ] <やること>(期限、関連 issue)
  ```
- **方針に関わる決定**は、該当するテーマ issue に D として追記する。「決定者」に `先生との相談 #<相談issue>` と書く。
- TODO が片付いたら、結果を書いて close する(段階ラベルは使わない)。

### F. サブ issue(任意)

数値や図を伴う大きな実験を、単独で参照したいときだけ切り出す。小さな決定は、親へのコメントで済ませる。サブ issue の本文にも、決定・背景・根拠・検討した代替案・影響を書く。`gh` からサブ issue を作れるかは環境による。作れなければ、新しい issue を作って親の本文の一覧に `#N` で並べる。

## 注意

- 苦情データなど、元データの内容や個人情報になり得る値は書かない。
- 非公開リポジトリでも、投稿内容は履歴に残る前提で書く。issue のコメントは編集・削除しても履歴に残り得る。
- 先生や共同研究者の発言を書くときは、相手に見られても問題ない書き方にする。
- 数値は、実際に実行して得た値だけを書く。推定値や記憶は書かない。
